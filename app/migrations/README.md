# Database migrations

This directory holds `sequelize-cli` migrations: each file describes
a schema change as a pair of `up` / `down` functions that the CLI
records in the `dbo.SequelizeMeta` table.

## Workflow

```bash
# Apply all pending migrations
npm run migrate

# Roll back the most-recently applied migration
npm run migrate:undo

# Show which migrations have been applied
npm run migrate:status

# Generate a skeleton migration file
npx sequelize-cli migration:generate --name add-some-thing
```

## Relationship to `setup/*.sql`

The `setup/TimeTracker.sql` and `setup/TimeEntry.sql` files describe
the **baseline schema** — what an empty database needs to look like
before the application can boot. They predate this migration system
and remain authoritative for first-time installs (used by
`docker compose up`'s setup service).

Migrations in this directory describe **changes** that happen AFTER
the baseline. The first one (a stub `20260516-baseline.js`) declares
the baseline applied so the CLI doesn't try to re-create existing
tables on an established database; new migrations added by this
project from here forward live as proper up/down pairs.

When the baseline + migration list converge cleanly, the SQL files
in `setup/` can be regenerated by walking every migration's up step.
That's a future cleanup; for now we keep both paths in sync by hand.

## Authoring guidelines

- **Always provide `down`.** Even if it's a no-op with a comment
  explaining why, every migration needs a rollback path.
- **Don't reference Sequelize models.** Migrations should manipulate
  the schema directly via `queryInterface`; models drift, schema
  doesn't.
- **Schema-qualify.** All this project's tables live in `dbo`. Use
  `queryInterface.createTable({ tableName: 'X', schema: 'dbo' }, ...)`
  rather than the un-qualified shorthand.
- **No data backfill in schema migrations.** Use a separate seeder
  or a one-shot script for that.
